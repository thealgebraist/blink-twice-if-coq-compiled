## 1. Normative W3C WebAuthn & Credential Management Requirements

The Web Authentication (WebAuthn) specification defines a **Credential ID** as a probabilistically-unique byte sequence identifying a public key credential source and its attestations. While early drafts of WebAuthn Level 1 left the upper bound of the Credential ID implementation-defined, subsequent iterations (WebAuthn Level 2 and Level 3) introduced strict normative bounds to ensure interoperability across FIDO2/CTAP2 authenticators, platform APIs, and Relying Parties (RPs).

### 1.1 Normative Citations (WebAuthn Level 3)
* **§ 5.1.3 (PublicKeyCredentialDescriptor Dictionary):** The `id` member contains the Credential ID of the public key credential the caller is referring to. When passed to `navigator.credentials.create()` (in `excludeCredentials`) or `navigator.credentials.get()` (in `allowCredentials`), the client and authenticator process this byte sequence.
* **§ 5.8.3 (Authenticator Data Structure - Attested Credential Data):** During credential generation (` authenticatorMakeCredential`), the authenticator produces `attestedCredentialData`, which embeds a 16-bit big-endian unsigned integer `credentialIdLength` ($L$), immediately followed by $L$ bytes of `credentialId`. The specification normatively states:
  > *"Credential IDs are generated by authenticators in two forms... Regardless of form, the minimum length of a Credential ID is 1 byte, and the maximum length is 1023 bytes."*
* **§ 6.3.3 (The `authenticatorGetAssertion` Operation):** When filtering `allowCredentials` or `excludeCredentials`, authenticators may ignore or reject credential descriptors whose `id` length violates protocol constraints. Specifically, CTAP2.1 defines `maxCredentialIdLength` in `authenticatorGetInfo` responses, and the WebAuthn specification caps valid Credential IDs at **1023 bytes** ($\le 1023$) and requires them to be non-empty ($> 0$).

## 2. Chromium Implementation Details & Architectural Invariants

In Chromium, WebAuthn requests originate in the Blink renderer (`third_party/blink/renderer/modules/credentialmanagement/`) and traverse the Mojo IPC boundary (`blink::mojom::Authenticator`) into the browser process (`content/browser/webauth/` and `device/fido/`).

### 2.1 Source Analysis: `device/fido/fido_constants.cc` & `device/fido/`
Chromium's FIDO layer enforces structural bounds on CTAP2/U2F messages and credential descriptors to prevent memory exhaustion, buffer overflows in USB/BLE HID transport frames, and CTAP2 CBOR serialization failures.

In `device/fido/fido_constants.h` and `device/fido/fido_constants.cc`, protocol constants govern the maximum allowable sizes of CTAP structures. Specifically:
```cpp
// Maximum length of a WebAuthn Credential ID in bytes, per WebAuthn Level 3.
constexpr size_t kMaxCredentialIdLength = 1023;
```
When processing `PublicKeyCredentialDescriptor` lists (`allow_credentials` or `exclude_credentials`) and parsing `AttestedCredentialData` (`device/fido/attested_credential_data.cc`), Chromium enforces the following invariants:

1. **Non-Empty Invariant ($l > 0$):** A zero-length Credential ID cannot uniquely identify a key handle on a security key or platform authenticator. In `AttestedCredentialData::ConsumeFromCtapResponse`, if the parsed 2-byte big-endian `credential_id_length` is `0`, parsing fails or the credential is rejected.
2. **Upper Bound Invariant ($l \le 1023$):** Although the 16-bit length field in `AttestedCredentialData` theoretically permits lengths up to $65535$ ($2^{16}-1$) bytes, CTAP2 transport packet limits and WebAuthn Level 3 mandate $l \le 1023$. Any incoming `PublicKeyCredentialDescriptor` or authenticator-generated ID exceeding `1023` bytes is dropped or triggers `CtapDeviceResponseCode::kCtap2ErrLimitExceeded` / `DOMException(NotAllowedError / InvalidStateError)`.

### 2.2 Security Implications of the Bound
* **Memory Safety & DoS Prevention:** Without strict enforcement of $l \le 1023$ at the Blink/FIDO boundary, a malicious RP could pass megabyte-sized `allowCredentials` arrays across Mojo IPC into the privileged browser process or down to low-memory external USB/NFC security tokens.
* **U2F / CTAP1 Backward Compatibility:** Legacy U2F authenticators encode key handles using an 8-bit length field ($0..255$). Modern CTAP2 authenticators use CBOR byte strings bounded by `maxCredentialIdLength` (bounded globally by WebAuthn at 1023 bytes). Enforcing $1 \le l \le 1023$ prevents integer truncation when down-casting lengths to 10-bit or 16-bit internal buffers.

Definition valid_cred_id_len (l : Z) : bool :=
  (0 <? l) && (l <=? 1023).

(** High-level propositional specification of a valid Credential ID length. *)
Definition ValidCredIDLenProp (l : Z) : Prop :=
  0 < l <= 1023.

(** Validation function over raw byte buffers using Zlength. *)
Definition validate_credential_id (cid : CredentialID) : ValidationResult :=
  let l := Zlength cid in
  if l <=? 0 then ErrEmptyCredentialID
  else if 1023 <? l then ErrCredentialIDTooLong
  else ValidCredentialID cid.

(** Boolean check over a CredentialID buffer directly. *)
Definition is_valid_credential_id (cid : CredentialID) : bool :=
  valid_cred_id_len (Zlength cid).
