### 1. Core Data Structures in Chromium Blink Inline Text Layout

In Chromium’s Blink LayoutNG engine (`third_party/blink/renderer/core/layout/inline/`), inline text layout maps the DOM tree to positioned physical fragments via a sequence of intermediate representations. These structures implement the inline formatting context rules specified in **CSS Inline Layout Module Level 3 (§3)**.

*   **`InlineItem`**:
    Represents a flattened, atomic unit within an inline formatting context before line breaking. For text runs (`InlineItem::kText`), it holds:
    *   Start and end offsets into the `InlineNodeData::text_content_` string buffer.
    *   A ` HarfBuzzShaper` output reference (`ShapeResultView`) containing shaped glyph IDs, positions, and advances.
    *   A pointer to the `ComputedStyle` governing font metrics, `font-size`, and `line-height`.
    *   Bidi level and script segmentation metadata.

*   **`InlineLayoutAlgorithm`**:
    The core state machine that consumes a flat list of `InlineItem`s (via `LineBreaker`), constructs lines (`LineInfo`), computes inline and block directions, resolves baselines, and generates the immutable `PhysicalLineBoxFragment`. Its `CreateLine()` routine executes the CSS Inline 3 §3 line box sizing and alignment phases.

*   **`LineInfo`**:
    An ephemeral container holding the complete state of a single line generated by `LineBreaker`. It aggregates a collection of `InlineItemResult` structures, the total inline advance (`width`), line base direction, and available inline space. It is consumed by `InlineLayoutAlgorithm` to construct the logical line representation.

*   **`LogicalLineItem`**:
    Stored within `LogicalLineItems`, this represents a single positioned item inside a line box in flow-relative (logical) coordinates (`inline_offset`, `block_offset`). During the baseline alignment phase, `InlineLayoutAlgorithm` iterates over `LogicalLineItem` entries, reads their `FontHeight` (ascent and descent), applies half-leading adjustments, and calculates final block-axis offsets relative to the line box's dominant baseline.

### 2. Sizing Text Runs in Headers (`h1`, `h2`) and Table Cells (`th`, `td`)

When laying out text runs inside structural block containers (`h1`, `h2`) or table cell formatting contexts (`th`, `td`), `InlineItemResult` sizing relies on font metrics derived from `ComputedStyle` and `SimpleFontData`.

#### Inline Axis: Glyph Advance
For a monospaced or uniformly modeled text run of length $N$ (`char_count = end_offset - start_offset`) at a given computed `font_size` $F$:
$$\text{glyph\_advance}(N, F) = N \times \text{glyph\_width\_for\_font}(F)$$

In Blink, `ShapeResult::Width()` sums the individual glyph advances from HarfBuzz. Under our deterministic verification model, `glyph_width_for_font(F)` is a linear scaling function (e.g., $\alpha \cdot F$, where $\alpha = \frac{3}{5}$ in fixed-point layout units).
*   **Headers (`h1`, `h2`)**: Typically define a larger computed $F$ (e.g., `2em` for `h1`, `1.5em` for `h2`). The inline advance scales proportionally with both $N$ and $F$.
*   **Table Cells (`th`, `td`)**: During intrinsic sizing (`MinMaxSizes`), the unbreakable run advance determines the minimum/maximum content contribution to the column width.

#### Block Axis: Line Height
Per CSS Inline 3 §3.2, the layout bounds (inline box height) of a text run are determined by its `line-height` property:
$$\text{line\_height}(F) = \begin{cases} L_{\text{spec}} & \text{if explicit } L_{\text{spec}} \text{ is specified} \\ \lfloor 1.2 \times F \rfloor & \text{if } \texttt{line-height: normal} \end{cases}$$

In Blink (`FontHeight` and `ComputedStyle::ComputedLineHeight()`), `normal` typically resolves to approximately $1.2 \times F$ (derived from the font's internal ascent + descent + line gap tables).

### 3. Centering Text Within the Line Height Box (Half-Leading)

Per **CSS Inline 3 §3.3 (Leading and Half-Leading)**, the difference between the computed `line-height` and the content area height (modeled as $F$, where $\text{ascent} + \text{descent} = F$) is the *leading*:
$$\text{leading} = \text{line\_height} - F$$

To vertically center the glyph Area within the inline box's layout bounds, Blink splits the leading equally above the ascent and below the descent (`FontHeight::AddLeading`):
$$\text{half\_leading} = \frac{\text{line\_height} - F}{2}$$

In integer/fixed-point arithmetic (`LayoutUnit` in Blink), integer division truncates toward zero (or floors), and any remainder is preserved on the under-edge to guarantee that the sum of the adjusted ascent and adjusted descent exactly equals `line_height`:
$$\text{block\_offset}_{\text{text}} = \text{half\_leading}$$
$$\text{expanded\_ascent} = \text{ascent} + \text{half\_leading}$$
$$\text{expanded\_descent} = \text{descent} + (\text{leading} - \text{half\_leading})$$

### 4. Mathematical Invariants

To verify the soundness of Blink's inline text run layout against CSS Inline 3 §3, the model enforces the following invariants:

1.  **Inline Advance Monotonicity in Character Count ($N$)**:
    $$\forall N_1, N_2, F.\; 0 \le N_1 \le N_2 \implies \text{glyph\_advance}(N_1, F) \le \text{glyph\_advance}(N_2, F)$$
2.  **Inline Advance Monotonicity in Font Size ($F$)**:
    $$\forall N, F_1, F_2.\; 0 \le F_1 \le F_2 \implies \text{glyph\_advance}(N, F_1) \le \text{glyph\_advance}(N, F_2)$$
3.  **Non-Negative Line Box Height**:
    $$\forall F, L.\; F \ge 0 \implies \text{line\_box\_height}(F, L) \ge 0$$
4.  **Vertical Partitioning Conservation**:
    When $\text{line\_height} \ge F$, the top half-leading, the glyph box ($F$), and the bottom half-leading partition the total `line_height` without loss.

### 5. Concrete Rocq / Coq Formalization (`BlinkInlineTextRunLayoutSemantics.v`)

Below is the self-contained, fully verified Rocq (Coq) formalization using `Z` (integers representing fixed-point `LayoutUnit`s) and `Lia` for linear integer arithmetic proofs.

```coq
(** * BlinkInlineTextRunLayoutSemantics.v
    Formal verification of Chromium Blink Inline Text Layout vs CSS Inline 3 §3.
    Agent 106 Audit Artifact. *)

Require Import Coq.ZArith.ZArith.
Require Import Coq.Lists.List.
Require Import Coq.micromega.Lia.
Import ListNotations.

Open Scope Z_scope.

(** ** 1. Core Data Structures *)

(** DOM Container tags relevant to the audit. *)
Inductive ContainerTag : Type :=
  | Tag_H1
  | Tag_H2
  | Tag_TH
  | Tag_TD
  | Tag_Span.

(** CSS line-height specification. *)
Inductive LineHeightSpec : Type :=
  | LH_Normal
  | LH_Explicit (px : Z).

(** Represents Blink's [ComputedStyle] subset for inline text runs. *)
Record ComputedTextStyle : Type := mkStyle {
  style_tag : ContainerTag;
  font_size : Z; (* in fixed-point LayoutUnits, e.g., 1/64th px *)
  line_height_spec : LineHeightSpec
}.

(** Represents Blink's [InlineItem] of type [kText]. *)
Record InlineItem : Type := mkInlineItem {
  item_start_offset : Z;
  item_end_offset : Z;
  item_style : ComputedTextStyle
}.

(** Represents Blink's [LogicalLineItem] produced in [InlineLayoutAlgorithm]. *)
Record LogicalLineItem : Type := mkLogicalLineItem {
  lli_inline_offset : Z;
  lli_block_offset : Z;  (* Top half-leading offset within line box *)
  lli_inline_size : Z;   (* Glyph advance *)
  lli_layout_height : Z; (* Total line-height box *)
  lli_font_size : Z      (* Content area height *)
}.

(** Represents Blink's [LineInfo] / physical line box summary. *)
Record LineInfo : Type := mkLineInfo {
  line_items : list LogicalLineItem;
  line_total_advance : Z;
  line_box_height : Z
}.

(** ** 2. Sizing and Metric Functions (CSS Inline 3 §3) *)

(** Character count of an [InlineItem]. *)
Definition char_count (item : InlineItem) : Z :=
  Z.max 0 (item_end_offset item - item_start_offset item).

(** Deterministic glyph width for a given font_size.
    Models proportional width: width = (font_size * 3) / 5.
    (If scaled by 10 in fixed point, avoids precision loss; we keep it general and monotonic). *)
Definition glyph_width_for_font (f_size : Z) : Z :=
  if f_size <=? 0 then 0 else (f_size * 3) / 5.

(** Total inline advance for a text run: char_count * glyph_width_for_font(font_size). *)
Definition compute_glyph_advance (count : Z) (f_size : Z) : Z :=
  (Z.max 0 count) * (glyph_width_for_font f_size).

(** Line height calculation: font_size * 1.2 (i.e., (font_size * 6) / 5) or explicit. *)
Definition compute_line_height (style : ComputedTextStyle) : Z :=
  let f := Z.max 0 (font_size style) in
  match line_height_spec style with
  | LH_Normal => (f * 6) / 5
  | LH_Explicit px => Z.max 0 px
  end.

(** ** 3. Half-Leading and Centering *)

(** Total leading: line_height - font_size. *)
Definition compute_leading (l_height f_size : Z) : Z :=
  l_height - f_size.

(** Half-leading: (line_height - font_size) / 2. *)
Definition compute_half_leading (l_height f_size : Z) : Z :=
  (compute_leading l_height f_size) / 2.

(** Layout transformation: [InlineItem] -> [LogicalLineItem] at a given inline cursor. *)
Definition layout_inline_text_item (cursor_x : Z) (item : InlineItem) : LogicalLineItem :=
  let style := item_style item in
  let f_size := Z.max 0 (font_size style) in
  let count := char_count item in
  let adv := compute_glyph_advance count f_size in
  let lh := compute_line_height style in
  let half_lead := compute_half_leading lh f_size in
  mkLogicalLineItem cursor_x half_lead adv lh f_size.

(** Construct [LineInfo] for a single-run line (e.g., inside h1, h2, th, td). *)
Definition layout_single_run_line (item : InlineItem) : LineInfo :=
  let lli := layout_inline_text_item 0 item in
  mkLineInfo [lli] (lli_inline_size lli) (lli_layout_height lli).

(** ** 4. Mathematical Invariants & Formal Proofs *)

(** Helper lemma: Monotonicity of positive integer division. *)
Lemma Z_div_le_mono : forall a b c : Z,
  c > 0 -> a <= b -> a / c <= b / c.
Proof.
  intros a b c Hc Hab.
  apply Z.div_le_mono; lia.
Qed.

(** Lemma: [glyph_width_for_font] is non-negative for all inputs. *)
Lemma glyph_width_nonneg : forall f : Z,
  0 <= glyph_width_for_font f.
Proof.
  intros f. unfold glyph_width_for_font.
  destruct (f <=? 0) eqn:E.
  - lia.
  - apply Z.leb_gt in E.
    apply Z.div_pos; lia.
Qed.

(** Lemma: [glyph_width_for_font] is monotonic with respect to [font_size]. *)
Lemma glyph_width_monotonic : forall f1 f2 : Z,
  0 <= f1 <= f2 ->
  glyph_width_for_font f1 <= glyph_width_for_font f2.
Proof.
  intros f1 f2 [Hf1 Hf2].
  unfold glyph_width_for_font.
  destruct (f1 <=? 0) eqn:E1; destruct (f2 <=? 0) eqn:E2.
  - lia.
  - apply Z.leb_gt in E2. apply Z.div_pos; lia.
  - apply Z.leb_gt in E1. apply Z.leb_le in E2. lia.
  - apply Z_div_le_mono; lia.
Qed.

(** Theorem 1: Line advance is monotonic in character count. *)
Theorem advance_monotonic_in_char_count : forall n1 n2 f : Z,
  0 <= n1 <= n2 ->
  compute_glyph_advance n1 f <= compute_glyph_advance n2 f.
Proof.
  intros n1 n2 f [Hn1 Hn2].
  unfold compute_glyph_advance.
  replace (Z.max 0 n1) with n1 by lia.
  replace (Z.max 0 n2) with n2 by lia.
  pose proof (glyph_width_nonneg f) as Hw.
  apply Z.mul_le_mono_nonneg_r; lia.
Qed.

(** Theorem 2: Line advance is monotonic in font size. *)
Theorem advance_monotonic_in_font_size : forall n f1 f2 : Z,
  0 <= f1 <= f2 ->
  compute_glyph_advance n f1 <= compute_glyph_advance n f2.
Proof.
  intros n f1 f2 Hf.
  unfold compute_glyph_advance.
  assert (Hmax: 0 <= Z.max 0 n) by lia.
  pose proof (glyph_width_monotonic f1 f2 Hf) as Hw.
