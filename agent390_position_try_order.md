**AGENT 390 AUDIT REPORT: Blink CSS `position-try` Sequential Evaluation Semantics**

### 1. Executive Summary
In Blink’s LayoutNG engine, CSS Anchor Positioning fallback resolution (`position-try-fallbacks`) is governed by a strict, deterministic, sequential evaluation model managed primarily by the `OutOfFlowLayoutPart` during the layout pass of an containing block. The engine iterates through a prioritized list of candidate styles, executing a speculative layout pass for each until a candidate satisfies containment constraints without overflowing its inset-modified containing block (IMCB).

---

### 2. Evaluation Candidate Queue Construction
Before iteration begins, Blink constructs a unified fallback evaluation queue for the out-of-flow (OOF) positioned element:

1. **Index 0 (Base Style):** The element's author-defined base styles (with `position-try` rules omitted).
2. **Index $1 \dots N$ (Fallback List):** The ordered comma-separated tokens defined in `position-try-fallbacks` (e.g., `@position-try` rules, `<try-tactic>` keywords like `flip-block`, or `position-area` values).

---

### 3. The Sequential Evaluation Loop (`OutOfFlowLayoutPart`)
When laying out an OOF node with `position-try` options, Blink enters a `TryCalculateOffset` loop. By default (assuming `position-try-order: normal`), the evaluation is strictly linear and short-circuiting.

#### Step A: Speculative Style Resolution
For the current index $i$ in the queue:
* If $i > 0$, Blink invokes ` StyleEngine::UpdateStyleForPositionTry` to recalculate the `ComputedStyle` of the OOF element.
* **Cascade Integration:** The properties inside the active `@position-try` block (or generated by a `<try-tactic>`) are injected into the cascade at the **Position Try Cascade Origin** (which sits above normal author styles, animations, and transitions, but below `!important` author/user/UA rules).
* Only the restricted subset of allowed properties (insets, margins, sizing, self-alignment, `position-anchor`, and `position-area`) are applied.

#### Step B: IMCB & Offset Calculation
Using the speculative `ComputedStyle`:
1. Blink resolves the target anchor(s) and computes the **Inset-Modified Containing Block (IMCB)** based on the containing block's geometry and the evaluated `inset-*` properties (`top`, `right`, `bottom`, `left`).
2. Blink resolves the element's used sizes (executing a speculative child layout pass on the OOF element if its intrinsic size depends on the new constraints, such as changing `width: auto` with new left/right insets).
3. Margin rules and alignment properties (`align-self`, `justify-self`) are applied to position the OOF margin box within the IMCB.

#### Step C: Overflow Interrogation (The Exit Condition)
Blink checks if the resulting OOF **margin box** fits strictly within the bounds of the **IMCB**:
* **Scrollable Adjustment:** If the containing block is a scroll container, the IMCB calculations account for current scroll offsets and default scroll-Snap areas, checking against the *scrollable containing block* edges where applicable.
* **Match Found (Short-Circuit):** If `margin_box` $\subseteq$ `IMCB` on all axes where insets are non-auto (no overflow occurs), **evaluation terminates immediately**. Blink commits the current `ComputedStyle` and layout result, discarding the remaining $i+1 \dots N$ candidates.
* **Overflow Detected:** If the margin box breaches any edge of the IMCB, the speculative layout result is discarded, $i$ is incremented, and the loop continues to Step A.

---

### 4. Exception: `position-try-order` Pre-Sorting
If `position-try-order` is set to a logical or physical dimension (`most-width`, `most-height`, `most-block-size`, `most-inline-size`), the purely sequential short-circuit model is modified:

1. **Pre-Evaluation Phase:** Blink iterates through *all* candidates ($0 \dots N$) upfront solely to compute the resulting IMCB dimensions for each option.
2. **Stable Sort:** The candidate list is re-ordered in descending order based on the available space in the specified axis of their respective IMCBs. If two candidates yield identical IMCB sizes, their original relative declaration order is preserved (stable sort).
3. **Standard Loop Resumption:** Blink then runs the standard Step 3 sequential evaluation loop (Speculative Style $\rightarrow$ Layout $\rightarrow$ Overflow Check) on the newly sorted list, short-circuiting at the first candidate whose margin box does not overflow its IMCB.

---

### 5. Exhaustion Semantics (All Candidates Fail)
If the loop exhausts all indices $0 \dots N$ and every single candidate results in an IMCB overflow, Blink triggers fallback exhaustion recovery:

1. **Last Successful Tracking (Anchor Scroll):** If the element was previously laid out successfully in an earlier frame/lifecycle, certain anchor-positioning stability heuristics may apply, though per current CSS Anchor Positioning specs, if *none* fit, it reverts.
2. **Reversion to Index 0:** Blink discards all `@position-try` overrides and reverts the element back to its **Base Style (Index 0)**, committing that layout despite the overflow.
3. **Visibility Suppression:** If `position-visibility: no-overflow` is specified on the element, exhaustion of the try-list flags the fragment as hidden, suppressing paint and hit-testing without affecting layout geometry.

### 6. Lifecycle & Inter-Frame State (`Element::EnsureAnchorScrollData`)
To prevent infinite layout loops during animations or scrolling:
* `position-try` evaluation occurs during the **Layout phase** of the Blink lifecycle.
* Because switching `@position-try` rules alters `ComputedStyle` *during* layout, Blink snapshots the successful try-option index on the layout result (`NGLayoutResult`). If a subsequent style recalc occurs without geometry changes, Blink caches the active `position-try` index to avoid thrashing the cascade until the next layout pass verifies containment.
