**AUDIT REPORT: Blink CSS Engine – `cqb` Unit Block-Size Resolution**
**Auditor:** Agent 397
**Target Subsystem:** `third_party/blink/renderer/core/css/` & `third_party/blink/renderer/core/layout/`
**Subject:** Container Query Block (`cqb`) Unit Evaluation Pipeline

---

### 1. Executive Summary
The `cqb` unit represents 1% of the computed block size of the nearest ancestor query container. In Blink’s LayoutNG architecture, resolving `cqb` requires decoupling logical axis mapping from physical dimensions until layout containment and writing modes of the *target container* are evaluated. This audit details the exact mechanism Blink uses to resolve the block size for `cqb` during style calculation and layout passes.

---

### 2. Core Classes & Data Structures
*   **`CSSToLengthConversionData`**: Holds the state required to convert relative CSS units into `LayoutUnit`s or `float` pixels. Specifically, its inner `ContainerSizes` struct caches the ancestor lookup chain.
*   **`ContainerQueryEvaluator`**: Attached to the container’s `ElementRareDataVector`. It stores the latest physical dimensions (`PhysicalSize`) and contained axes (`PhysicalAxes`) generated by the LayoutNG pass.
*   **`PhysicalAxes` / `LogicalAxes`**: Bitmask enums used to verify whether the block axis is validly contained by the container-type property.

---

### 3. Resolution Pipeline

#### Phase 1: Ancestor Container Lookup
When `CSSToLengthConversionData::ContainerSizes` is invoked to resolve a `cqb` value on a target element:
1. Blink traverses the flat tree ancestors (`FlatTreeTraversal::ParentElement`).
2. It searches for the nearest ancestor whose `ComputedStyle` specifies a valid `container-type` that supports block-axis queries.
3. **Validation condition:** To resolve `cqb`, the container must establish **Inline and Block size containment** (`container-type: size`). *Note: `container-type: inline-size` is insufficient for `cqb` and will cause Blink to skip the container and continue walking up the tree.*

#### Phase 2: Axis Mapping (Logical to Physical)
A critical nuance in the Blink implementation is that `cqb` is resolved against the **container’s** writing mode, not the styled element’s writing mode.
1. Once the target container element is identified, Blink retrieves the *container’s* `ComputedStyle`.
2. It inspects `container_style.GetWritingMode()` (via `WritingModeConverter`).
3. The logical **block axis** (`kLogicalAxisBlock`) is translated into a physical axis (`kPhysicalAxisHorizontal` or `kPhysicalAxisVertical`):
   *   If the container is `horizontal-tb`: Block Axis $\rightarrow$ **Physical Vertical Axis (Height)**.
   *   If the container is `vertical-rl`, `vertical-lr`, `sideways-rl`, or `sideways-lr`: Block Axis $\rightarrow$ **Physical Horizontal Axis (Width)**.

#### Phase 3: Extracting the Evaluated Size
With the physical axis determined, Blink queries the container's `ContainerQueryEvaluator`:
1. The `StyleEngine` ensures that layout is up to date up to the container via the interleaved style/layout pass (LayoutNG).
2. During `NGBlockNode::Layout()`, the container’s `LayoutBox` calculates its **content box** size (excluding borders, padding, and scrollbars).
3. This `PhysicalSize` is passed to `ContainerQueryEvaluator::ContainerChanged()`.
4. `CSSToLengthConversionData` requests the dimension corresponding to the mapped physical axis:
   *   For `kPhysicalAxisVertical`: Extracts `physical_size.height.ToDouble()`.
   *   For `kPhysicalAxisHorizontal`: Extracts `physical_size.width.ToDouble()`.
5. **Calculation:** The final `1cqb` base value is computed as `extracted_dimension / 100.0`.

---

### 4. Fallback & Edge-Case Handling (The "Small Viewport" Fallback)
Audit verifies that Blink adheres to the CSS Conditional Rules Level 5 specification when `cqb` cannot be resolved against a container:

*   **Condition A: No Ancestor Container Found.**
*   **Condition B: Ancestor Container lacks Block Containment** (e.g., ancestor is `container-type: inline-size`, which only contains the inline axis).
*   **Condition C: Container is Disconnected or `display: none` / `display: contents`.**

**Blink Resolution Behavior:**
If any of the above conditions are met, `ContainerSizes` returns `std::nullopt` for the block size. `CSSToLengthConversionData` immediately falls back to the **Small Viewport Size** (`svb` equivalent). 
*   Blink queries `ViewportSize` for the root `Document`.
*   It maps the block axis using the **root element's** writing mode, returning 1% of the small viewport height (`svh`) or width (`svw`) accordingly.

---

### 5. Style/Layout Interleaving & Dependency Tracking
To prevent infinite loops during `cqb` resolution:
1. When an element resolves `cqb`, `CSSToLengthConversionData` sets a flag on the element's `ComputedStyleBuilder`: `SetHasContainerRelativeUnits()`.
2. If the container's block size changes in a subsequent layout pass, `ContainerQueryEvaluator` marks style as dirty for all descendants bearing this flag (`kContainerUnitChange`).
3. Because `container-type: size` enforces `contain: size`, the descendants' resolved `cqb` dimensions cannot cyclically alter the container's block size, preserving DAG (Directed Acyclic Graph) integrity in LayoutNG.

**Audit Status:** `cqb` block-size resolution in Blink is **COMPLIANT** with W3C CSS Containment Module Level 3. **End of Report.**
