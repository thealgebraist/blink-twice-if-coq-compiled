### 1. Core Data Structures in Blink Grid Item Placement

In Chromium’s LayoutNG Grid implementation (`third_party/blink/renderer/core/layout/grid/`), CSS Grid Layout Level 1 §8 is realized through four primary structures that bridge style resolution and physical track sizing:

*   **`GridSpan`** (`grid_span.h`): Represents a resolved half-open interval $[start\_line, end\_line)$ or an unresolved indefinite span during initial parsing.
    *   *States*: `kDefinite` (resolved zero-based indices after offset translation) or `kIndefinite` ( carries only a positive `span_size`, awaiting auto-placement).
    *   *Coordinate Translation*: Because CSS allows negative placement and implicit tracks before the explicit grid, `GridSpan` stores indices shifted by `explicit_grid_offset` so that the minimum occupied grid line across all items normalizes to index `0`.
*   **`GridLineResolver`** (`grid_line_resolver.h`): Stateless utility encapsulated within `ComputedStyle` and `GridPlacement` that resolves raw `GridPosition` values (`grid-row-start`, `grid-column-end`, etc.) into integer line indices or span counts.
    *   *Inputs*: Explicit track counts (`explicit_grid_column_count`, `explicit_grid_row_count`), named line maps (`NamedGridLinesMap` from `grid-template-columns`/`rows`), and implicit named lines generated by `grid-template-areas`.
    *   *Responsibilities*: Evaluates raw CSS positions into untranslated explicit coordinates (where `0` is the first explicit line, negative numbers precede the explicit grid, and values $> \text{explicit\_count}$ exceed it).
*   **`GridPlacementData`** (`grid_placement.h`): The output payload of the placement algorithm and input to track sizing.
    *   *Fields*: `Vector<GridArea> grid_item_positions` (indexed by item order), `wtf_size_t explicit_grid_column_count`, `wtf_size_t explicit_grid_row_count`, and the negative implicit track offsets (`column_start_offset`, `row_start_offset`).
    *   *Subgrid extensions*: Carries `line_resolver` context down to nested subgrids so they can resolve parent-named lines relative to the subgrid's spanned interval.
*   **`GridPlacement`** (`grid_placement.cc`): The state machine executing the W3C §8.5 placement algorithm.
    *   *Internal Structures*: `GridPositionVector` of items partitioned into three priority queues (definite in both axes, definite in major axis, indefinite in both), an `AutoPlacementCursor` `(major_position, minor_position)`, and a compressed 2D occupancy structure (`GridTrackOccupancyMap` / bit-matrix of occupied cells).

### 2. Grid Item Placement Algorithm

Blink implements W3C CSS Grid Layout Level 1 §8.5 inside `GridPlacement::RunAutoPlacementAlgorithm()`. The algorithm defines the **major axis** as the axis matching `grid-auto-flow` (`row` $\to$ rows, `column` $\to$ columns) and the **minor axis** as the orthogonal axis.

#### Phase 0: Pre-sorting and Definite Resolution
Before placement, items are sorted by their CSS `order` property (stable sort preserving DOM order for ties). `GridLineResolver` resolves all explicit positions. If an item has definite positions in both axes, its `GridArea` is fixed immediately. While doing this, Blink computes the minimum negative line index across all items to establish the `start_offset` for both axes, shifting the coordinate system so all indices are $\ge 0$, and sizes the occupancy matrix to the maximum known end line (`minor_max_end_line`).

#### Phase 1: Definite Both-Axes Placement
All items with definite `GridSpan`s in both the major and minor axes are written directly into the occupancy matrix.

#### Phase 2: Definite Major-Axis Placement (W3C §8.5 Step 2)
Items that have a definite span in the major axis (e.g., `grid-row: 2 / 4` when `grid-auto-flow: row`) but an indefinite span in the minor axis (`grid-column: auto / span 2`) are processed next.
*   **Sparse Packing (Default)**: Blink maintains a per-major-track minor-axis cursor (`minor_cursors[major_line]`). For an item locked to major span $[M_{start}, M_{end})$, the starting minor search index is $\max_{m \in [M_{start}, M_{end})} \text{minor\_cursors}[m]$. The cursor increments until an unoccupied contiguous block of size `minor_span` is found across all rows $m \in [M_{start}, M_{end})$. If it exceeds `minor_max_end_line`, the implicit grid expands in the minor axis. Once placed, $\text{minor\_cursors}[m]$ is updated to the item's `minor_end` for that major span.
*   **Dense Packing (`dense`)**: The search always resets to minor line `0` for the locked major span $[M_{start}, M_{end})$, scanning upward for the first available gap.

#### Phase 3: Remaining Auto-Placed Items (W3C §8.5 Step 4)
Items remaining (either definite in the minor axis and auto in the major axis, or auto in both axes) are processed using a single global `AutoPlacementCursor` $(C_{major}, C_{minor})$ initialized to $(0, 0)$ (if `dense` is specified, the cursor resets to $(0, 0)$ at the start of every item's search).

1.  **Definite Minor Axis, Indefinite Major Axis**:
    *   If `dense`, set $C_{major} = 0$.
    *   Set $C_{minor}$ to the item's definite `minor_start`. (If the item's `minor_start` is less than the current cursor's $C_{minor}$ in sparse mode, increment $C_{major}$ by 1 first).
    *   Increment $C_{major}$ until the region $[C_{major}, C_{major} + \text{major\_span}) \times [\text{minor\_start}, \text{minor\_end})$ is completely unoccupied. Expand the major-axis implicit grid if necessary.
2.  **Indefinite in Both Axes**:
    *   If `dense`, reset $(C_{major}, C_{minor}) \leftarrow (0, 0)$.
    *   Loop:
        *   If $C_{minor} + \text{minor\_span} > \text{minor\_max\_end\_line}$, advance the cursor to the next major track: $C_{major} \leftarrow C_{major} + 1$, $C_{minor} \leftarrow 0$. (Note: If the item's `minor_span` alone is larger than `minor_max_end_line`, `minor_max_end_line` is grown to fit `minor_span` during step 3 of §8.5 before this loop runs).
        *   Check if $[C_{major}, C_{major} + \text{major\_span}) \times [C_{minor}, C_{minor} + \text{minor\_span})$ is free in the occupancy map.
        *   If free, place the item, mark occupancy, and in sparse mode set $C_{minor} \leftarrow \text{placed\_minor\_end}$ (leaving $C_{major}$ at $\text{placed\_major\_start}$).
        *   If occupied, advance $C_{minor}$ past the obstructing item's `minor_end` and repeat.

### 3. Line Resolution and Negative Index Normalization

`GridLineResolver` translates CSS 1-based line indices (and negative indices counting backward from the end of the explicit grid) into 0-based untranslated explicit indices, where `0` is the first explicit line and $E$ (the number of explicit tracks) is the last explicit line (so there are $E + 1$ explicit lines: $0, 1, \dots, E$).

#### Integer Line Normalization
Given a non-zero CSS integer $L \in \mathbb{Z} \setminus \{0\}$ and an explicit track count $E \in \mathbb{N}$:
$$\text{resolve}(L, E) = \begin{cases} 
L - 1 & \text{if } L > 0 \\
(E + 1) + L & \text{if } L < 0 
\end{cases}$$
*   **Example ($-1$ Normalization)**: If a grid defines `grid-template-columns: 100px 100px` ($E = 2$), there are $E + 1 = 3$ explicit lines (0, 1, 2). A CSS line of `-1` resolves to $(2 + 1) + (-1) = 2$, which is the trailing edge of the explicit grid. If $E = 0$ (no explicit tracks), $E + 1 = 1$, so `-1` resolves to line `0`. If $L = -5$ and $E = 2$, it resolves to $3 - 5 = -2$, creating two implicit tracks *before* the explicit grid.

#### Named Line Resolution & Fallback
When a position specifies a `<custom-ident>` (with an optional integer index $k \neq 0$, defaulting to $k=1$):
1.  Blink merges explicit named lines (from `grid-template-columns`/`rows`, including `repeat()` expansions) with implicit named lines (from `grid-template-areas`, where area `foo` generates `foo-start` and `foo-end` lines).
2.  Let $M(\text{ident}) = [i_0, i_1, \dots, i_{m-1}]$ be the sorted list of 0-based explicit line indices bearing that name.
3.  **Positive $k > 0$**: If $k \le m$, the line resolves to $i_{k-1}$. If $k > m$, W3C §8.3 states that excess occurrences are assumed to exist on every implicit track in the positive direction. Blink computes:
    $$\text{line} = E + (k - m)$$
    *(Special Case: If $m = 0$—the name does not exist at all—every implicit track is assumed to have the name, so it resolves to $E + k$).*
4.  **Negative $k < 0$**: Counting backward from the end of $M$. Let $k' = |k|$. If $k' \le m$, the line resolves to $i_{m - k'}$. If $k' > m$, it overflows into the negative implicit grid:
    $$\text{line} = -(k' - m)$$

#### Conflict Resolution (W3C §8.3.1 Grid Placement Conflict Handling)
After resolving `start` ($S$) and `end` ($D$) for an item:
*   If both $S$ and $D$ are definite integers:
    *   If $S > D$, swap them: $(S, D) \leftarrow (D, S)$.
    *   If $S = D$, increment the end line: $D \leftarrow S + 1$.
*   If one is definite and the other is a `span N` ($N \ge 1$):
    *   Definite $S$, span $N$: $D \leftarrow S + N$.
    *   Definite $D$, span $N$: $S \leftarrow D - N$.
*   If both are spans or `auto`, the position becomes an **Indefinite Span** of size $N$ (where `auto` has $N=1$). (If a named span like `span foo` is used with a definite start $S$, Blink scans forward from $S+1$ for the $N$-th occurrence of `foo`, falling back to implicit lines past $E$ if not found).

### 4. Mathematical Invariants, Edge Cases, and Gaps

#### Mathematical Invariants
1.  **Strict Span Positivity**:
    $$\forall \text{item}, \quad \text{end\_line}(\text{item}) - \text{start\_line}(\text{item}) \ge 1$$
2.  **Non-Negative Shifted Normalization**:
    Let $\Delta = -\min(0, \min_{\text{item} \in \text{Definite}} \text{start\_line}(\text{item}))$. After applying the offset translation $L' = L + \Delta$:
    $$\forall \text{item}, \quad 0 \le \text{start\_line}'(\text{item}) < \text{end\_line}'(\text{item}) \le \text{kMaxGridLines}$$
3.  **Disjointness of Auto-Placed Items**:
    Let $A(i) = [r_{s}(i), r_{e}(i)) \times [c_{s}(i), c_{e}(i))$ be the 2D interval of item $i$. If item $j$ is placed via Phases 2 or 3 (i.e. $j$ is not Definite in both axes), then for all items $i$ placed *prior* to $j$:
    $$A(i) \cap A(j) = \emptyset$$
    *(Note: Two items $i, k$ that are BOTH definite in both axes CAN overlap: $A(i) \cap A(k) \neq \emptyset$ is permitted by CSS Grid).*
4.  **Sparse Cursor Monotonicity**:
    In `sparse` mode, for the sequence of items $j_1, j_2, \dots, j_n$ placed in Phase 3, the global cursor positions $(C_{major}^{(t)}, C_{minor}^{(t)})$ are lexicographically non-decreasing:
    $$C_{major}^{(t)} < C_{major}^{(t+1)} \lor \left(C_{major}^{(t)} = C_{major}^{(t+1)} \land C_{minor}^{(t)} \le C_{minor}^{(t+1)}\right)$$

#### Edge Cases & Implementation Gaps (Blink vs. W3C Spec)
*   **Track Clamping (`kGridMaxTracks = 100000` / Legacy `1000`)**: W3C §8.3 does not define a hard maximum on grid tracks, only noting that implementations may cap track counts to prevent OOM. Blink clamps resolved lines and spans to `kGridMaxTracks`. **Gap/Quirk**: If an item is placed at `grid-column: 150000 / span 5`, after clamping both start and end to `100000`, the naive clamping produces $S = D = 100000$, violating Invariant 1. Blink explicitly shifts `start_line = end_line - 1` (or truncates the span) when clamping at the upper boundary so that `end_line - start_line >= 1` holds and `end_line <= kGridMaxTracks`.
*   **Span Overflow on Definite End Line in Subgrids**: In a subgrid, the implicit grid cannot expand; all items are clamped to the subgrid's explicit track count $[0, E_{sub}]$. If an item inside a subgrid specifies `grid-column-end: 2; grid-column-start: span 5;`, raw resolution gives $[-3, 2)$. Blink shifts and clamps this to $[0, 2)$ (reducing the span size from 5 to 2) rather than shifting the end line to `5`, matching the CSS Grid Level 2 subgrid clamping rules.
