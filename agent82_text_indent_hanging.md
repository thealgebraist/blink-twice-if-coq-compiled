### 1. Core Data Structures in Blink Inline Indentation

In Chromium’s Blink rendering engine (specifically within the `core/layout/inline/` subsystem, formerly LayoutNG), inline indentation and hanging punctuation are resolved during the line-breaking phase (`LineBreaker`) and committed into intermediate line representations (`LineInfo`) before box fragment generation (`InlineLayoutAlgorithm`).

```
+-------------------------------------------------------------------+
|                        ComputedStyle                              |
|  - TextIndentLength (Length: Fixed | Percent | Calc)              |
|  - TextIndentLine   (kFirstLine | kEachLine)                      |
|  - TextIndentType   (kNormal | kHanging)                          |
|  - HangingPunctuation (Bitmask: kNone | kFirst | kLast |          |
|                                 kForceEnd | kAllowEnd)            |
+-------------------------------------------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|                         LineBreaker                               |
|  - Evaluates `ShouldIndentText()` based on `BreakToken` state.    |
|  - Computes `text_indent` inline-size offset.                     |
|  - Scans `InlineItem` stream for hanging glyphs (Unicode Zs, Ps,  |
|    Pe, Pi, Pf, Po categories) to adjust `available_width_`.       |
+-------------------------------------------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|                           LineInfo                                |
|  - text_indent_: LayoutUnit (Inline offset applied to line start) |
|  - hang_width_: LayoutUnit (Trailing hanging space / Punctuation) |
|  - hang_start_width_: LayoutUnit (Leading hanging punctuation)    |
|  - available_width_: LayoutUnit (BFC inline constraint)           |
|  - width_: LayoutUnit (Consumed inline advance of items)          |
+-------------------------------------------------------------------+
```

#### `ComputedStyle` Primitives
*   **`TextIndent`**: Represented via `Length` (resolved to `LayoutUnit` via `MinimumValueForLength`). Accompanied by two bitfield enumerations:
    *   `TextIndentLine`: `kFirstLine` (default), `kEachLine` (CSS Text Level 3 `each-line` keyword).
    *   `TextIndentType`: `kNormal` (default), `kHanging` (CSS Text Level 3 `hanging` keyword).
*   **`HangingPunctuation`**: A strongly-typed bitmask (`uint8_t`) defined in `computed_style_constants.h`:
    *   `kNone = 0x0`, `kFirst = 0x1`, `kLast = 0x2`, `kForceEnd = 0x4`, `kAllowEnd = 0x8`.

#### `InlineItem` & `InlineItemResult`
*   **`InlineItem`**: Represents an atomic unit within the flat `InlineNodeData` text buffer. Items of type `InlineItem::kText` map to contiguous runs of the `text_content_` string sharing identical `ComputedStyle` and script properties, backed by a `ShapeResult`.
*   **`InlineItemResult`**: Generated by `LineBreaker` as it consumes `InlineItem`s for a single line. Contains `inline_size` (the shaped advance width), `text_offset` ranges, and boolean flags such as `has_hanging_spaces` or `can_hang_punctuation`.

#### `LineInfo`
`LineInfo` is the state accumulator for a single formatted line. The critical spatial fields governing §9 semantics are:
*   `LayoutUnit text_indent_`: The computed inline-start offset introduced by `text-indent`.
*   `LayoutUnit available_width_`: The net inline size available for placing content after subtracting floats and `text_indent_`.
*   `LayoutUnit width_`: The accumulated inline size of all `InlineItemResult`s placed on the line.
*   `LayoutUnit hang_width_`: The advance width of trailing collapsible spaces or `allow-end`/`force-end`/`last` hanging punctuation that extends beyond the line box's inline-end edge.

### 2. First Formatted Line Detection and `text-indent` Offset Application

According to CSS Text Level 3 §9.1, `text-indent` specifies the indentation applied to lines of inline content in a block. Blink evaluates this in `LineBreaker::ShouldIndentText()` and applies the offset during `LineBreaker::PrepareNextLine()`.

#### Detection of Indented Lines
Let a line $L$ be parameterized by its incoming `InlineBreakToken` $T_{in}$. The boolean predicate $\text{ShouldIndent}(L)$ is determined by:
1.  **First Formatted Line (`is_first_formatted_line`)**: True if $T_{in} = \text{null}$ (the very first line of the block container) AND the block is not an anonymous block continuation split by a block-in-inline child (`!is_after_forced_break` is false here; rather, it checks `!PreviousBreakToken()`).
2.  **After Forced Break (`is_after_forced_break`)**: True if $T_{in} \neq \text{null}$ and $T_{in}\text{.IsForcedBreak()}$ is true (caused by an explicit `<br>`, a preserved newline `\n` when `white-space` preserves newlines, or the initial line of the block).

Let $M_{\text{line}} \in \{\texttt{FirstLine}, \texttt{EachLine}\}$ and $M_{\text{type}} \in \{\texttt{Normal}, \texttt{Hanging}\}$. The raw indentation applicability predicate $\mathcal{P}_{\text{raw}}$ is:

$$\mathcal{P}_{\text{raw}} = \begin{cases} \text{is\_first\_formatted\_line} & \text{if } M_{\text{line}} = \texttt{FirstLine} \\ \text{is\_first\_formatted\_line} \lor \text{is\_after\_forced\_break} & \text{if } M_{\text{line}} = \texttt{EachLine} \end{cases}$$

The `hanging` keyword inverts the selection of lines:

$$\text{ShouldIndent} = \mathcal{P}_{\text{raw}} \oplus (M_{\text{type}} = \texttt{Hanging})$$

*(where $\oplus$ denotes logical XOR).*

#### Offset Resolution (Positive, Negative, and Percentage)
Let $W_{\text{cb}}$ be the inline-size of the containing block’s content box (`ConstraintSpace::AvailableSize().inline_size`). When $W_{\text{cb}}$ is indefinite (e.g., during intrinsic min/max-content size calculation), percentage indents resolve to $0$. Otherwise, the raw indent $I_{\text{raw}}$ is resolved from `ComputedStyle::TextIndent()`:

$$I_{\text{raw}} = \begin{cases} v & \text{if } \text{Fixed}(v) \\ \lfloor \frac{p}{100} \times W_{\text{cb}} \rfloor_{\text{LayoutUnit}} & \text{if } \text{Percent}(p) \land W_{\text{cb}} \neq \text{Indefinite} \\ 0 & \text{if } \text{Percent}(p) \land W_{\text{cb}} = \text{Indefinite} \end{cases}$$

The effective line indent $I_{\text{eff}}$ stored in `LineInfo::SetTextIndent` is:

$$I_{\text{eff}} = \begin{cases} I_{\text{raw}} & \text{if } \text{ShouldIndent} = \text{true} \\ 0 & \text{otherwise} \end{cases}$$

#### Impact on Line Breaking and Positioning
When $I_{\text{eff}}$ is applied to a line with base available width $W_{\text{avail\_base}}$ (which is $W_{\text{cb}}$ minus float intrusions):
1.  **Available Width Adjustment**: `LineBreaker` updates its capacity:
    $$W_{\text{avail}} = W_{\text{avail\_base}} - I_{\text{eff}}$$
    *   **Positive Indent ($I_{\text{eff}} > 0$)**: Reduces $W_{\text{avail}}$. If $I_{\text{eff}} \ge W_{\text{avail\_base}}$, $W_{\text{avail}} \le 0$. Blink’s `LineBreaker` enforces progress by guaranteeing at least one grapheme cluster or atomic inline is placed on the line (unless the line is empty), causing controlled inline overflow.
    *   **Negative Indent ($I_{\text{eff}} < 0$)**: Increases $W_{\text{avail}}$ ($W_{\text{avail}} > W_{\text{avail\_base}}$). Content begins outside the inline-start edge of the content box (protruding into the margin/padding area) and can consume the extra width before wrapping at the normal inline-end edge.
2.  **Physical / Logical Box Offset**: In `InlineLayoutAlgorithm::CreateLine`, the line box’s inline-start offset (`line_box_offset.inline_offset`) is shifted by $+I_{\text{eff}}$ relative to the BFC inline-start offset (for `text-align: start/left`).

### 3. Hanging Punctuation Offset Calculation

CSS Text Level 3 §9.2 stipulates that hanging punctuation glyphs are not considered when measuring the line's contents for fit, alignment, or justification. Depending on the keyword, the glyphs hang outside the line box's start or end edge.

*(Audit Note: While WebKit implements full support for `hanging-punctuation`, Chromium Blink’s LayoutNG historically implemented trailing whitespace hanging via `LineInfo::HangWidth()` and partial CJK punctuation hanging in `ShapingLineBreaker`. The specification mechanics and Blink's architectural integration points operate as follows).*

```
Line Box Start Edge                                   Line Box End Edge
        |<-------------------- W_avail -------------------->|
  [Hang]|===================================================|[Hang]
  (First|               Measured Line Content               |(Last / End
   Punc)|                                                   | Punc)
  <---->|                                                   |<---->
   H_s                                                         H_e
```

#### Glyph Classification & Advance Extraction
Let $G_1, G_2, \dots, G_n$ be the sequence of shaped glyphs on the line, with corresponding advance widths $w(G_i) \ge 0$ extracted via `ShapeResultView::CharacterPosition` or HarfBuzz glyph metrics.
*   **`first`**: An opening bracket or quote at the very start of the first formatted line (Unicode categories `Ps`, `Pi`, `Pf`, or specific ASCII quotes `U+0027`, `U+0022`). Let $H_s$ be its advance width:
    $$H_s = \begin{cases} w(G_1) & \text{if } (\texttt{kFirst} \in \text{HP}) \land \text{is\_first\_formatted\_line} \land \text{IsOpeningPunct}(G_1) \\ 0 & \text{otherwise} \end{cases}$$
*   **`last`**: A closing bracket or quote at the end of the last formatted line (or before a forced break) belonging to `Pe`, `Pf`, `Pi`, or ASCII quotes:
    $$H_{\text{last}} = \begin{cases} w(G_n) & \text{if } (\texttt{kLast} \in \text{HP}) \land \text{is\_last\_line\_or\_forced} \land \text{IsClosingPunct}(G_n) \\ 0 & \text{otherwise} \end{cases}$$
*   **`allow-end` / `force-end`**: A stop or comma at the end of a line (`U+002C`, `U+002E`, `U+060C`, `U+06D4`, `U+3001`, `U+3002`, `U+FF0C`, `U+FF0E`, `U+FE50`–`U+FE52`, `U+FF61`, `U+FF64`).
    *   Under `allow-end`, the glyph hangs *only if* it does not otherwise fit prior to justification:
        $$H_{\text{allow}} = \begin{cases} w(G_n) & \text{if } (\texttt{kAllowEnd} \in \text{HP}) \land \text{IsStopOrComma}(G_n) \land \left(\sum_{i=1}^n w(G_i) - H_s > W_{\text{avail}}\right) \\ 0 & \text{otherwise} \end{cases}$$
    *   Under `force-end`, the glyph unconditionally hangs if it falls at the line edge (and is excluded from justification measurement):
        $$H_{\text{force}} = \begin{cases} w(G_n) & \text{if } (\texttt{kForceEnd} \in \text{HP}) \land \text{IsStopOrComma}(G_n) \\ 0 & \text{otherwise} \end{cases}$$

*(Note: By spec, at most one punctuation character may hang at each edge of the line).*
Thus, total trailing hanging punctuation width is:
$$H_e = \max(H_{\text{last}}, H_{\text{allow}}, H_{\text{force}})$$

#### Line Breaking and Alignment Mechanics
1.  **Line Fit (LineBreaker)**: During `LineBreaker::BreakText`, the effective capacity of the line is transiently expanded by $H_s$ at the start of the line, and candidate trailing tokens are permitted to overshoot $W_{\text{avail}}$ by up to $H_e$ without triggering a soft wrap:
    $$\sum_{i=1}^{n} w(G_i) \le W_{\text{avail}} + H_s + H_e$$
2.  **Line Box Placement & Alignment (`InlineLayoutAlgorithm::ApplyTextAlign`)**:
    *   The start edge of the line's inline content is shifted by $-H_s$ relative to the indented line start ($I_{\text{eff}} - H_s$).
    *   For alignment (`center`, `end`, `justify`), the net occupied width of the line is treated as:
        $$W_{\text{net}} = \left(\sum_{i=1}^{n} w(G_i)\right) - H_s - H_e$$
    *   The remaining free space for alignment/justification is computed as $S_{\text{free}} = W_{\text{avail}} - W_{\text{net}}$.
    *   When `text-align: justify` is active and `force-end` is set, any stop/comma at the end of the line is excluded from $W_{\text{net}}$ (via $H_e = w(G_n)$), ensuring the rest of the line expands to fill $W_{\text{avail}}$ while $G_n$ hangs outside the inline-end edge.
