## 1. Normative W3C/WHATWG Specification Requirements

Under the Web Platform's Same-Origin Policy (SOP), scripts executing within one browsing context (e.g., an `iframe` or `window.open` popup) frequently obtain references to the `WindowProxy` of another browsing context. While holding a cross-origin `WindowProxy` reference is permitted to enable frame navigation and `postMessage` communication, arbitrary property inspection or mutation across origin boundaries is strictly prohibited to prevent universal Cross-Site Scripting (UXSS) and cross-origin data exfiltration.

### 1.1 HTML Standard §7.2.3.1: `CrossOriginProperties ( O )`
The WHATWG HTML Standard defines an explicit allowlist of properties accessible on a `Window` (via its `WindowProxy` exotic object) when the incumbent settings object is not same-origin-domain with the target `Window` object's relevant settings object.

For a `Window` object $O$, the abstract operation `CrossOriginProperties(O)` returns a list of Property Descriptor records limited strictly to the following keys:

1. **Navigation & Hierarchy Attributes (Getters only)**:
   - `window`
   - `self`
   - `frames`
   - `parent`
   - `top`
   - `length`
   - `closed`
2. **Cross-Origin Mutable Attributes (Getters and Setters)**:
   - `location` (Returns the cross-origin `Location` object or navigates the frame on `[Set]`)
   - `opener` (Getter returns the opener `WindowProxy`; Setter is actually restricted or replaces via ordinary property semantics depending on context, though listed in the cross-origin property descriptor table as `[Get]` only in modern specs to prevent cross-origin opener spoofing).
3. **Cross-Origin Invocable Methods (Values)**:
   - `blur`
   - `close`
   - `focus`
   - `postMessage`

### 1.2 Abstract Operations: `[[GetOwnProperty]]`, `[[Get]]`, `[[Set]]`, and `CrossOriginGetOwnPropertyHelper`
When a script performs property access $O[P]$ on a `WindowProxy` object:

1. **Same-Origin Check**: The engine executes `IsPlatformObjectSameOrigin(O)`. This compares the *effective script origin* (or origin, if `document.domain` is not used) of the current Realm's settings object with that of the target `Window` $O$.
2. **Same-Origin Execution**: If `IsPlatformObjectSameOrigin(O)` returns `true`, the `WindowProxy` delegates directly to `OrdinaryGetOwnProperty`, `OrdinaryGet`, or `OrdinarySet` on the underlying `Window` instance, granting full access to the DOM, global variables, and prototype chain.
3. **Cross-Origin Execution**: If `IsPlatformObjectSameOrigin(O)` returns `false`:
   - Indexed property access ($P$ is an array index $< \text{child\_frame\_count}$) resolves to the corresponding child `WindowProxy`.
   - Named property access ($P$ matches a `<iframe name="...">` where the target document allows cross-origin named access, though increasingly restricted) or explicit safelisted property access checks `CrossOriginGetOwnPropertyHelper(O, P)`.
   - If $P \in \text{CrossOriginProperties}(O)$ and the requested operation (`Get` vs `Set`) matches the descriptor capabilities in the safelist, the operation succeeds.
   - **Then- Clause / Fallback**: For any property $P \notin \text{CrossOriginProperties}(O)$ (excluding valid cross-origin indexed/named frames and symbol `then`, `@@toStringTag`, `@@hasInstance`, `@@isConcatSpreadable` which return `undefined` without throwing to support Promise resolution and DevTools inspection), the specification mandates throwing a `"SecurityError"` `DOMException`.

## 2. Chromium Blink Implementation & Invariants

In Chromium's Blink rendering engine, the `Window` interface is bifurcated into `LocalDOMWindow` (when the frame is hosted in the same renderer process) and `RemoteDOMWindow` (when Site Isolation places the frame in an out-of-process iframe, or OOPIF). Both inherit from `DOMWindow` (`third_party/blink/renderer/core/frame/dom_window.cc`).

### 2.1 Architecture in `dom_window.cc` and V8 Bindings
Blink enforces HTML §7.2 through a synthesis of V8 Interceptor callbacks generated by the WebIDL compiler (`v8_window.cc`) and security checks inside `BindingSecurity` and `DOMWindow`.

1. **V8 Access Check Callbacks**:
   The `Window` WebIDL interface is annotated with `[CheckSecurity=Receiver]`. In V8, the `ObjectTemplate` for `V8Window` is configured with `SetAccessCheckCallbackAndHandler`:
   - **Access Check Callback**: `BindingSecurity::ShouldAllowAccessTo(LocalDOMWindow* accessing_window, const DOMWindow* target)`
   - **Cross-Origin Interceptors**: `NamedPropertyGetterCallback`, `NamedPropertySetterCallback`, `IndexedPropertyGetterCallback`.

2. **Origin Evaluation (`BindingSecurity` & `SecurityOrigin`)**:
   When V8 accesses a property on a `WindowProxy`, it invokes the access check callback:
   ```cpp
   // Conceptual flow in third_party/blink/renderer/bindings/core/v8/binding_security.cc
   // and third_party/blink/renderer/core/frame/dom_window.cc
   bool BindingSecurity::ShouldAllowAccessTo(const LocalDOMWindow* accessing_window,
                                             const DOMWindow* target,
                                             ErrorReportOption reporting_option) {
     if (!target) return false;
     const Frame* frame = target->GetFrame();
     if (!frame || !frame->GetSecurityContext()) return false;
     
     const SecurityOrigin* accessing_origin = accessing_window->GetSecurityOrigin();
     const SecurityOrigin* target_origin = frame->GetSecurityContext()->GetSecurityOrigin();
     
     // Evaluates same-origin-domain (host, scheme, port, and document.domain mutation)
     return accessing_origin->CanAccess(target_origin);
   }
   ```
    note that if `target` is a `RemoteDOMWindow`, `CanAccess` is guaranteed to be `false` (or handled via cross-Origin interceptors directly, as `RemoteDOMWindow` possesses no local V8 context for arbitrary JS execution).

3. **Interceptor Dispatch for Safelisted Properties**:
   When `CanAccess` returns `false`, V8 blocks normal prototype and own-property lookup on the `Window` object and falls back to the cross-origin interceptors generated in `v8_window.cc`.
   - The generated table `kCrossOriginAttributeTable` and `kCrossOriginOperationTable` strictly mirror `CrossOriginProperties(O)`.
   - Specifically, attributes with `[CrossOrigin]` or `[CrossOrigin=(Setter)]` in `window.idl`:
     ```webidl
     [CheckSecurity=Receiver, ImplementedAs=DOMWindow]
     interface Window : EventTarget {
       [CrossOrigin] readonly attribute WindowProxy window;
       [CrossOrigin] readonly attribute WindowProxy self;
       [CrossOrigin, PutForwards=href, LegacyUnforgeable] readonly attribute Location location;
       [CrossOrigin] void close();
       [CrossOrigin] readonly attribute boolean closed;
       [CrossOrigin] void focus();
       [CrossOrigin] void blur();
       [CrossOrigin] readonly attribute WindowProxy frames;
       [CrossOrigin] readonly attribute unsigned long length;
       [CrossOrigin] readonly attribute WindowProxy? top;
       [CrossOrigin] attribute any opener; // Restricted in setter if cross-origin
       [CrossOrigin] readonly attribute WindowProxy? parent;
       [CrossOrigin] void postMessage(any message, USVString targetOrigin, optional sequence<object> transfer = []);
     };
     ```

4. **Violation Reporting (`dom_window.cc`)**:
   If a cross-origin access attempts to read or write a non-safelisted property (e.g., `document`, `localStorage`, `eval`, `alert`, or custom globals), V8 routes the failed access to `DOMWindow::ReportCoopAccess` and `BindingSecurity::FailedAccessCheckFor`:
   - In `dom_window.cc`, `DOMWindow::SanitizedCrossDomainAccessErrorMessage` and `DOMWindow::CrossDomainAccessErrorMessage` construct the exact `"SecurityError"` message while carefully avoiding leaking cross-origin information (such as the target's full URL path or origin if the caller is sandboxed).

### 2.2 Core Security Invariants in `dom_window.cc`
- **Invariant 1 (Complete Mediation)**: No property read, write, define, or delete on a `DOMWindow` bypasses the V8 AccessCheck + `SecurityOrigin::CanAccess` gate.
- **Invariant 2 (Default Deny)**: If `is_cross_origin` is true (`!accessing_origin->CanAccess(target_origin)`), any property $p$ not explicitly marked `[CrossOrigin]` in the IDL (or a valid cross-origin child frame index/name or JS engine symbol exception) must fail and throw a `SecurityError`.
- **Invariant 3 (RemoteDOMWindow Isolation)**: A `RemoteDOMWindow` never satisfies `!is_cross_origin` for full property access; its C++ implementation in `dom_window.cc` only implements the backing methods for `[CrossOrigin]` IDL operations (`close`, `focus`, `blur`, `postMessage`, etc.).
- **Invariant 4 (Write Restriction on Safelisted Getters)**: Even if a property is safelisted for `Get` (e.g., `window.top`, `window.parent`, `window.closed`), a cross-origin `Set` operation is denied unless the property is explicitly safelisted for `Set` (i.e., `location`).

Below is the self-contained, formal verification module `BlinkCrossOriginWindowProxyRestrictionsSemantics.v`. It models origins, `DOMWindow` states, property identifiers, operation types, the WHATWG HTML §7.2 safelist, and Blink's access control decision engine.

*)

(** ** 1. Domain Modeling: Origins, Properties, and Operations *)

(** We represent Web Origins (scheme, host, port, and optional domain override)
    via unique integer identifiers for decidable equality. *)
Record SecurityOrigin : Type := mkOrigin {
  scheme_id : Z;
  host_id   : Z;
  port      : Z;
  is_opaque : bool
}.

(** Decidable equality on Z using Z.eqb *)
Definition origin_same_origin_domain (o1 o2 : SecurityOrigin) : bool :=
  if o1.(is_opaque) || o2.(is_opaque) then
    false (* Opaque origins (e.g. sandboxed iframes without allow-same-origin) never match in CanAccess unless identical reference, modeled conservatively here as distinct *)
  else
    (o1.(scheme_id) =? o2.(scheme_id)) &&
    (o1.(host_id)   =? o2.(host_id)) &&
    (o1.(port)      =? o2.(port)).

(** Inverse of CanAccess: determines if the access across WindowProxy is cross-origin. *)
Definition compute_is_cross_origin (accessing target : SecurityOrigin) : bool :=
  negb (origin_same_origin_domain accessing target).
