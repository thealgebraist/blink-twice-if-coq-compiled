### 1. Core Data Structures in Blink Inline Formatting (LayoutNG)

In Chromium’s Blink engine, the Inline Formatting Context (IFC) transforms a flat sequence of DOM-derived inline items into a fragmented box tree hierarchy per line box, corresponding to the model defined in **CSS Inline Layout Module Level 3 §3 (Inline Box Model)**.

#### `InlineItem`
Produced during the Pre-Layout phase (`InlineNode::CollectInlines`), `InlineItem` represents a flattened, sequential token of the inline formatting context tree.
*   **Types (`InlineItemType`):** `kText`, `kControl`, `kOpenTag`, `kCloseTag`, `kAtomicInline`, `kFloat`, `kOutOfFlowPositioned`, `kBidiControl`.
*   **Payload:** 
    *   Offsets `[start_offset, end_offset)` into the `InlineNodeData::text_content_` UTF-16 string buffer (where non-text items like `kAtomicInline` or `kOpenTag` map to `U+FFFC` Object Replacement Characters or zero-length ranges).
    *   `LayoutObject*` pointing to the underlying Blink layout node.
    *   `ComputedStyle*` providing CSS property values (`margin`, `border`, `padding`, `vertical-align`, `box-decoration-break`).
    *   `ShapeResult*` (for `kText` items) containing HarfBuzz glyph clusters and advances.

#### `LineInfo`
Generated by `LineBreaker::NextLine`, `LineInfo` encapsulates the resolved sequence of `InlineItemResult` instances that fit within the available inline-size of a single line box.
*   **Structure:** Contains a `Vector<InlineItemResult>` representing the broken slice of `InlineItem`s, the line's base direction (`TextDirection`), available width, and line-end metrics.
*   **`InlineItemResult`:** Pairs an `InlineItem` reference with line-specific fragments: `TextOffsetRange`, resolved `inline_size` (`LayoutUnit`), `ShapeResultView`, and flags like `has_edge` (indicating whether start/end borders, padding, and margins apply on this specific line).

#### `InlineBoxState` and `InlineLayoutStateStack`
Managed during the Line Box Construction phase (`InlineLayoutAlgorithm::CreateLine`), `InlineBoxState` represents an active, open inline box (`<span>`, `<a>`, or the root inline box) within the current line.
*   **Fields:**
    *   `fragment_start`: Index in the `LogicalLineItems` buffer where this box's contents begin.
    *   `item`: Reference to the originating `InlineItem`.
    *   `style`: Reference to the box's `ComputedStyle`.
    *   `font_metrics`: Ascent/descent values derived from the primary font.
    *   `text_metrics`: Accumulated union of ascent/descent including leading.
    *   `margin_inline_start`, `margin_inline_end`, `border_edges`, `padding_edges`: Resolved `LayoutUnit` metrics for box edges.
    *   `pending_descendants`: Vector of child elements awaiting vertical alignment resolution (e.g., `vertical-align: top | bottom`).
*   **`InlineLayoutStateStack`:** A contiguous stack `Vector<InlineBoxState>` representing the ancestor chain of open inline boxes at the current inline-axis cursor position.

#### `LogicalLineItem` (`LogicalLineItems`)
An intermediate, flat vector of positioned layout items within a line box, ordered visually (post-Bidi reordering) or logically (pre-Bidi reordering), prior to conversion into immutable `PhysicalFragment` instances.
*   **Variants:** Can hold a text fragment (`ShapeResultView`), an open/close marker, an existing `PhysicalBoxFragment` (from an atomic inline), or a Culled Inline reference.
*   **Coordinates:** Maintains a `LogicalRect` (`rect.offset.inline_offset`, `rect.offset.block_offset`, `inline_size`, `block_size`).

### 2. Stack-Based Inline Box Hierarchy Management

CSS Inline 3 §3.1 specifies that an inline box can be split across multiple line boxes, and §3.4 dictates how margins, borders, and padding (MBP) are applied at the inline-start and inline-end edges of these fragments depending on `box-decoration-break`.

```
DOM: <p>Text <span>A <b>B [LINE BREAK] C</b> D</span></p>

Line 1 Stack Evolution:
1. Init Root Inline Box -> Stack: [Root]
2. "Text "              -> Append Text to Root
3. <span> (kOpenTag)    -> Push(span), Add start MBP -> Stack: [Root, span]
4. "A "                 -> Append Text to span
5. <b> (kOpenTag)       -> Push(b), Add start MBP    -> Stack: [Root, span, b]
6. "B"                  -> Append Text to b
7. [LINE BREAK]         -> Flush Stack (Clone/Slice):
                           Pop(b) (No end MBP if slice)
                           Pop(span) (No end MBP if slice)
                           Pop(Root)

Line 2 Stack Reconstruction:
1. Init Root Inline Box -> Stack: [Root]
2. ReconstructOpenTags  -> Push(span) (No start MBP if slice)
                        -> Push(b) (No start MBP if slice) -> Stack: [Root, span, b]
3. "C"                  -> Append Text to b
4. </b> (kCloseTag)     -> Pop(b), Add end MBP       -> Stack: [Root, span]
5. " D"                 -> Append Text to span
6. </span> (kCloseTag)  -> Pop(span), Add end MBP    -> Stack: [Root]
```

#### Pushing (`HandleOpenTag`)
When `InlineLayoutAlgorithm` encounters an `InlineItem` of type `kOpenTag`:
1.  **Compute Edges:** `LineBreaker` sets `item_result.has_edge` if the box is non-culled (has borders, padding, margins, background, or positioning).
2.  **Push State:** `box_states_->OnOpenTag()` allocates a new `InlineBoxState` at the top of `InlineLayoutStateStack`.
3.  **Advance Cursor:** The current inline-axis cursor (`position`) is advanced by `margin_inline_start + border_inline_start + padding_inline_start`.
4.  **Record Start:** `box_state.fragment_start` is set to the current `LogicalLineItems::size()`, reserving a placeholder slot for the resulting box fragment.

#### Popping (`HandleCloseTag`)
When encountering `kCloseTag`:
1.  **Advance Cursor:** The inline-axis cursor (`position`) is advanced by `padding_inline_end + border_inline_end + margin_inline_end`.
2.  **Compute Box Geometry:** `box_states_->OnCloseTag()` pops the top `InlineBoxState`. The total inline-size of the box fragment is computed as:
    $$\text{inline\_size} = (\text{position} - \text{margin\_inline\_end}) - \text{start\_position}$$
3.  **Vertical Alignment:** The popped box's block-offset and metrics (ascent/descent) are shifted according to its `vertical-align` property and merged into the parent `InlineBoxState` (now at the top of the stack) via ` FontHeight::Unite()`.
4.  **Create Box Item:** The placeholder at `box_state.fragment_start` in `LogicalLineItems` is populated with the finalized geometry, encompassing all child items between `fragment_start` and the current buffer index.

#### Line Breaks (`box-decoration-break: slice | clone`)
When a line breaks while the `InlineLayoutStateStack` has depth $> 1$ (excluding the root inline box):
*   **End of Line $N$:** `InlineLayoutStateStack::OnEndPlaceItems` iterates through all remaining open `InlineBoxState`s from top to bottom.
    *   If `box-decoration-break: slice` (default), `padding_inline_end`, `border_inline_end`, and `margin_inline_end` are suppressed ($0$).
    *   If `box-decoration-break: clone`, the end edges are fully applied, advancing `position` and expanding the box fragment's `inline_size`.
    *   All open boxes are popped and converted into `PhysicalBoxFragment`s for Line $N$.
*   **Start of Line $N+1$:** The `InlineBreakToken` carries the current `item_index` into the next line. Before processing items at `item_index`, Blink traverses the ancestor chain of `kOpenTag` items that remain unclosed.
    *   It reconstructs the stack by pushing an `InlineBoxState` for each open ancestor.
    *   If `box-decoration-break: slice`, start MBP edges are suppressed ($0$).
    *   If `box-decoration-break: clone`, start MBP edges are re-applied, advancing Line $N+1$'s initial cursor `position`.

### 3. Atomic Inline Box Integration

Per **CSS Inline 3 §3.1**, atomic inlines (such as `inline-block`, `inline-table`, `inline-flex`, and replaced elements like `<img>`) participate in the inline formatting context as a single, opaque, unbreakable glyph-like box.

1.  **Tokenization:** During `CollectInlines`, an atomic inline is emitted as a single `InlineItem` of type `kAtomicInline` (occupying 1 character `U+FFFC` in `text_content_`), without `kOpenTag` or `kCloseTag` children in the same IFC.
2.  **Sub-Layout during Line Breaking:** When `LineBreaker` encounters `kAtomicInline`, it invokes a sub-layout algorithm (e.g., `BlockLayoutAlgorithm`) to produce a `LayoutResult` containing a `PhysicalBoxFragment`. The resolved `inline_size` + `margin_inline_start` + `margin_inline_end` is evaluated against the remaining line width.
3.  **Stream Integration:** In `InlineLayoutAlgorithm::PlaceAtomicInline`:
    *   The cursor `position` is advanced by `item_result.margins.inline_start`.
    *   A `LogicalLineItem` wrapping the `LayoutResult` is appended at `position`.
    *   The cursor `position` is advanced by `fragment.InlineSize() + item_result.margins.inline_end`.
4.  **Baseline Synthesis & Metric Propagation:**
    *   Unlike non-replaced inline boxes (whose metrics derive from font `ascent` and `descent`), an atomic inline synthesizes its baseline metrics based on its `baseline-source` (`first`, `last`) or defaults to its margin-box bottom edge (for `inline-block` with `overflow != visible` or replaced elements).
    *   `InlineLayoutStateStack::ComputeInlinePositions` queries `BoxStrut` metrics from the atomic inline, applies `vertical-align` shifting relative to the parent `InlineBoxState`'s baseline, and merges the resulting `FontHeight` (`ascent`, `descent`) directly into the active `InlineBoxState` at the top of the stack.

### 4. Mathematical Invariants

Let $\Sigma$ be the sequence of `InlineItem` tokens for a single line box (augmented with reconstructed open tags at the start of the line and implicit close tags at the end of the line). Let $S_t$ be the `InlineLayoutStateStack` at step $t \in [0, |\Sigma|]$, and $P_t \in \mathbb{Q}$ (modeled as `LayoutUnit` or $\mathbb{Z}$ in fixed-point) be the inline-axis advance cursor at step $t$.

#### Invariant 1: Per-Line Stack Balancedness
For any valid line stream $\Sigma = [e_1, e_2, \dots, e_n]$ after boundary normalization (reconstructing open tags at line-start, flushing unclosed tags at line-end):
$$\forall t \in [1, n], \quad |S_t| \ge 1 \quad (\text{Root Inline Box is always present})$$
$$|S_0| = 1 \implies |S_n| = 1$$
Furthermore, if $e_i = \text{OpenTag}(id)$ pushes state onto $S$ at depth $d$, the corresponding pop at depth $d$ is triggered by $e_j = \text{CloseTag}(id)$ where $j > i$, and $\forall k \in (i, j), |S_k| \ge d$.

#### Invariant 2: Advance Monotonicity (Under Non-Negative Margins)
Assuming all resolved inline margins $m_{\text{start}}, m_{\text{end}} \ge 0$, border widths $b \ge 0$, padding $p \ge 0$, text glyph advances $\Delta_{\text{text}} \ge 0$, and atomic inline sizes $\Delta_{\text{atomic}} \ge 0$:
$$\forall t \in [0, n-1], \quad P_{t+1} \ge P_t$$
More generally, allowing negative margins $m \in \mathbb{Z}$, the cursor satisfies the exact additive conservation law:
$$P_n - P_0 = \sum_{e \in \Sigma_{\text{text}}} \Delta(e) + \sum_{e \in \Sigma_{\text{atomic}}} (\Delta(e) + m_{\text{start}}(e) + m_{\text{end}}(e)) + \sum_{e \in \Sigma_{\text{open}}} \text{Edge}_{\text{start}}(e) + \sum_{e \in \Sigma_{\text{close}}} \text{Edge}_{\text{end}}(e)$$

#### Invariant 3: Determinism of Tree Construction
Given an initial line state $\sigma_0 = (S_0, P_0, L_0)$ (where $L_0$ is the initial `LogicalLineItems` buffer) and a normalized token stream $\Sigma$, the transition relation $\sigma_0 \xrightarrow{\Sigma} \sigma_n$ is a total, deterministic function:
$$\forall \sigma, \sigma', \sigma'', \quad (\sigma \xrightarrow{\Sigma} \sigma' \land \sigma \xrightarrow{\Sigma} \sigma'') \implies \sigma' = \sigma''$$
